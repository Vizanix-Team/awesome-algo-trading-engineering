## 1. Что такое биржевой API и из чего он состоит

Биржевой API (application programming interface, программный интерфейс) — это набор правил, по которым внешняя программа может взаимодействовать с системами биржи: получать данные о ценах, отправлять заявки, проверять баланс счёта, отменять открытые заявки. По сути это тот же принцип, что и API любого веб-сервиса, с которым вы, возможно, уже работали, только вместо данных о погоде или списка товаров в интернет-магазине вы получаете и отправляете финансовую информацию, где ошибка в запросе может стоить реальных денег.

Практически любой биржевой API состоит из двух принципиально разных частей, которые решают разные задачи. Первая часть — REST API (или похожий на него интерфейс на основе запросов и ответов), используемый для разовых команд: узнать баланс счёта, отправить заявку, отменить заявку, запросить исторические данные за прошлый период. Вторая часть — потоковый интерфейс, обычно на основе протокола WebSocket, используемый для получения непрерывного потока обновлений: изменения цены в реальном времени, обновления стакана заявок, статус исполнения ваших собственных заявок.

Понимание этого разделения — первый шаг к проектированию собственной торговой системы. Разовые команды и запросы данных естественно ложатся на REST, а всё, что требует немедленной реакции на изменения в реальном времени, требует потокового соединения. Смешение этих двух подходов, например, постоянный опрос REST API вместо подписки на поток через WebSocket, работает, но неэффективно и создаёт задержку, которая может быть критична для стратегии, чувствительной ко времени реакции.

## 2. REST API: запрос-ответ для данных и команд

REST API работает по принципу "запрос-ответ": ваша программа отправляет HTTP-запрос на определённый адрес биржи с нужными параметрами, а биржа отправляет обратно ответ, обычно в формате JSON, содержащий запрошенные данные или подтверждение выполненной команды. Каждый такой запрос независим от предыдущих: биржа не хранит "состояние разговора" между запросами, кроме того, что явно закодировано в самом запросе, например через идентификатор сессии или ключ доступа.

Типичный набор операций, доступных через REST API биржи, включает: получение списка доступных торговых инструментов и их параметров (минимальный размер заявки, шаг цены), получение текущего снимка стакана заявок или последних сделок, получение баланса счёта и списка открытых позиций, отправку новой заявки с указанием актива, направления, объёма и цены, отмену ранее отправленной заявки по её идентификатору, и запрос истории собственных сделок за прошлый период.

Важная особенность работы с REST API для торговли — необходимость аккуратно обрабатывать задержку между отправкой запроса и получением ответа. В отличие от простого запроса данных, где задержка в полсекунды обычно не критична, для отправки заявки эта задержка означает, что рыночная цена могла успеть измениться за время между вашим решением и моментом, когда заявка реально попала в стакан биржи. Хороший клиент API для торговли всегда фиксирует время отправки запроса и время получения ответа, чтобы иметь возможность анализировать эту задержку впоследствии.

## 3. WebSocket: постоянный поток обновлений

Протокол WebSocket устанавливает постоянное соединение между вашей программой и сервером биржи, по которому сервер может отправлять новые данные в любой момент, без необходимости, чтобы клиент заново запрашивал их. Это принципиально отличается от модели "запрос-ответ" REST API: вы один раз подписываетесь на определённый поток данных, например обновления стакана заявок для конкретного актива, и затем биржа сама присылает вам каждое изменение по мере его появления.

Эта модель гораздо эффективнее для данных, которые меняются часто и должны обрабатываться с минимальной задержкой. Представьте разницу между постоянным звонком другу каждую секунду с вопросом "что нового?" и подпиской на его сообщения, которые приходят сами, как только что-то происходит. Первый подход тратит ресурсы на большинство звонков, где ответ "ничего нового", второй передаёт информацию именно тогда, когда она появляется, и ничего больше.

Работа с WebSocket в коде требует немного другого стиля программирования по сравнению с обычными последовательными HTTP-запросами: обычно используется асинхронная модель или модель с обратными вызовами (callback), где ваш код регистрирует функцию, которая будет вызвана автоматически при получении нового сообщения от сервера. Для начинающего это первое естественное знакомство с асинхронным программированием, и стоит выделить отдельное время на его освоение, потому что почти любая система реального времени в этой области будет полагаться на этот подход.

## 4. Аутентификация и ключи доступа

Для операций, требующих доступа к личному счёту (проверка баланса, отправка заявок), биржа должна убедиться, что запрос действительно исходит от владельца счёта, а не от постороннего. Стандартный механизм для этого — пара ключей API: публичный идентификатор ключа (API key) и секретный ключ (API secret), которые вы получаете в личном кабинете биржи после соответствующей настройки.

Механизм аутентификации обычно работает так: для каждого запроса, требующего авторизации, ваша программа формирует криптографическую подпись запроса с использованием секретного ключа, обычно через алгоритм на основе хеш-функции, и прикладывает эту подпись вместе с публичным идентификатором ключа к запросу. Биржа на своей стороне пересчитывает такую же подпись, используя хранимый у себя секретный ключ, и сверяет её с присланной, подтверждая, что запрос отправлен владельцем ключа и не был изменён по дороге.

Критически важное практическое правило для начинающего: секретный ключ API никогда не должен попадать в код, который вы публикуете в открытый репозиторий, в логи, или в любое другое место, доступное посторонним. Стандартная практика — хранить ключи в переменных окружения или в специализированном хранилище секретов, отдельно от исходного кода программы, и подключать библиотеки для проверки кода на случайную утечку секретов перед публикацией репозитория. Многие биржи также позволяют ограничить права конкретного ключа, например разрешить только чтение данных без права отправки реальных заявок, что разумно использовать при первых экспериментах.

## 5. Жизненный цикл заявки через API

Когда вы отправляете заявку через API, она проходит через несколько состояний, и понимание этого жизненного цикла критично для правильной работы торговой системы. Сразу после отправки заявка находится в состоянии "принята" (new или accepted): биржа подтвердила получение заявки и поставила её в очередь стакана заявок, но сделка ещё не произошла. Заявка может затем перейти в состояние "частично исполнена" (partially filled), если только часть объёма заявки нашла встречную сторону, оставаясь в стакане с оставшимся объёмом.

Если весь объём заявки исполнился, она переходит в конечное состояние "полностью исполнена" (filled). Если вы или система отменяете заявку до полного исполнения, она переходит в состояние "отменена" (canceled). Некоторые биржи также имеют состояние "отклонена" (rejected), когда заявка не прошла базовую проверку биржи сразу при отправке, например из-за недостаточного баланса счёта или нарушения минимального размера заявки.

Важный практический нюанс: подтверждение о смене состояния заявки может приходить как в ответе на сам REST-запрос отправки заявки, так и отдельным сообщением через поток WebSocket, и хорошая архитектура клиента должна аккуратно обрабатывать оба источника информации, не дублируя обработку одного и того же события. Также стоит помнить, что между отправкой запроса на отмену заявки и подтверждением отмены заявка теоретически может успеть частично или полностью исполниться, поэтому код никогда не должен предполагать, что заявка отменена, пока не пришло явное подтверждение от биржи.

## 6. Ограничения скорости запросов и как с ними жить

Практически все биржи вводят ограничения на скорость запросов (rate limits) к своему API, чтобы защитить свою инфраструктуру от перегрузки. Ограничение может выражаться, например, в максимальном числе запросов в минуту или в максимальном "весе" запросов за период, где разные типы запросов имеют разный вес в зависимости от того, насколько они нагружают серверы биржи. Превышение лимита обычно приводит к временной блокировке доступа для вашего ключа API, иногда на несколько минут, а при систематическом злоупотреблении и на более длительный срок.

Для торговой системы это означает необходимость активно следить за собственной скоростью запросов и строить логику так, чтобы не приближаться к лимиту в обычных условиях работы. Хорошая практика — реализовать в клиенте API счётчик использованных запросов за текущий период и искусственно замедлять или откладывать не критичные по времени запросы, если счётчик приближается к пределу, оставляя запас для действительно срочных операций, таких как отмена заявки в момент резкого движения рынка.

Многие биржи также присылают в заголовках HTTP-ответа информацию о текущем состоянии лимита: сколько запросов уже использовано и когда лимит обнулится. Использование этой информации напрямую, а не попытка угадать лимит эмпирически, — более надёжный подход к построению устойчивого клиента API.

## 7. Обработка ошибок и разрывов соединения

Сетевые соединения не бывают идеально надёжными: REST-запрос может завершиться таймаутом, WebSocket-соединение может неожиданно разорваться из-за проблем на стороне сервера биржи, вашего интернет-провайдера, или промежуточной сетевой инфраструктуры. Торговая система, которая не готова к этим сбоям, рискует принимать решения на основе устаревших данных или вовсе перестать реагировать на рынок в критический момент.

Для REST-запросов стандартная практика — реализовать логику повторных попыток (retry) с разумной задержкой между попытками, но с осторожностью: для операции отправки заявки бездумный повторный запрос при таймауте опасен, потому что первая заявка может на самом деле уже быть принята биржей, и повторная отправка приведёт к дублированию сделки. Правильный подход — сначала проверить текущее состояние через отдельный запрос (например, запросить список открытых заявок), прежде чем повторно отправлять команду, которая могла и не была потеряна.

Для WebSocket-соединений необходима логика автоматического переподключения при разрыве, с повторной подпиской на все нужные потоки данных сразу после восстановления соединения. Также критично помнить, что за время разрыва соединения вы могли пропустить важные обновления, например изменения стакана заявок или статуса своих заявок, и после переподключения разумно запросить свежий снимок текущего состояния через REST API, чтобы синхронизировать локальное представление системы с реальным состоянием на бирже, а не полагаться только на пропущенный поток обновлений.

## 8. От песочницы к реальному счёту

Большинство серьёзных бирж предоставляют тестовую среду, часто называемую песочницей (sandbox) или тестовой сетью (testnet), которая имитирует боевой API биржи, но работает с виртуальными деньгами и часто с искусственными или задержанными данными. Это безопасное место для начинающего, чтобы отладить код взаимодействия с API: проверить аутентификацию, отправку и отмену заявок, обработку потоковых данных, не рискуя ни единым центом реальных средств.

Переход от песочницы к реальному счёту стоит делать постепенно и осознанно. Первый шаг — убедиться, что вся базовая функциональность работает корректно в песочнице в течение достаточно длительного времени, включая обработку ошибочных ситуаций, которые вы можете сымитировать намеренно. Второй шаг — подключение к реальному API биржи, но первое время только для чтения данных, без прав на отправку реальных заявок, чтобы убедиться, что аутентификация и обработка потоков работают так же, как в песочнице, поскольку реальные данные могут содержать пограничные случаи, отсутствующие в тестовой среде.

Третий шаг — включение прав на реальную торговлю, но с минимальным возможным объёмом капитала, ровно на тот срок, который нужен для проверки, что весь жизненный цикл заявки, обсуждённый выше, работает корректно с реальными деньгами и реальными задержками сети. Только после устойчивой работы на этом минимальном объёме разумно постепенно увеличивать выделенный капитал под контролем модуля управления рисками, о котором рассказывает отдельная книга в этой библиотеке.

## Итоги

- Биржевой API обычно разделён на REST для разовых команд и WebSocket для непрерывного потока обновлений в реальном времени.
- Секретный ключ API требует строгой защиты и никогда не должен попадать в открытый код или общедоступные логи.
- Заявка проходит через явный жизненный цикл состояний, и торговая система должна отслеживать эти состояния, а не предполагать результат отправленной команды.
- Ограничения скорости запросов требуют активного контроля со стороны клиента, а не реакции постфактум на блокировку.
- Переход от тестовой песочницы к реальному счёту стоит делать постепенно: сначала только чтение, затем минимальный объём торговли, затем постепенное увеличение капитала.
